# Final execution contract — written before final data exist

This document implements, without relaxing, the registered V2 decision rule.
Final data are not generated by unit tests, analysis tests, or the development
pipeline. Unit fixtures are fabricated log probabilities, not model outcomes.

1. Complete fresh full TRAIN/DEV optimization and the fixed stronger DEV text
   baseline. Independently re-derive the selected checkpoint from all trained
   DEV checks: minimum correct full-vocabulary CE, earlier step on ties. Do not
   select by test accuracy, random-control results or the latest checkpoint.
   An investigator can stop on a DEV failure without burning the final set.
   Recompute CE from stored label-log-probability tensors and run
   `dev_reproduce.py`: every condition on the selected checkpoint must exactly
   reproduce the stored full DEV outputs, with stock/disabled/zero parity and
   unchanged receiver parameters. This is verification, not new model selection.
2. `final_v2.py freeze` checks completion, mechanics, source/extension identity,
   checkpoint and endpoint identities. It writes one exclusive FINAL_FREEZE.json
   only when no final directory, outputs or final text run exists. Freeze both
   attention implementation and the exact text/analysis execution code, runtime
   source, model/tokenizer file identities, task/split seeds and scoring rule.
3. `channel_v2.py prepare --split final` materializes exactly the registered seed
   44002, 256 groups/1024 records, and captures sender states with the unchanged
   pipeline. Captured inputs are independently checked against the deterministic
   generator and manifests. It is not a checkpoint/architecture selection split.
4. `final_v2.py score` executes the frozen selected bridge with all seven core
   conditions: receiver-only, correct, shuffled, two norm-matched randoms, zero,
   original text. No final-output inspection before freeze. No generation.
   Run actual stock/disabled/zero full-vocabulary parity, independently check
   endpoint identity, and rerun fixed first32 cases with the **original full-set
   donor/random memories**, not newly constructed subset controls.
5. After that process unloads its model, `text_baseline.py --split final` runs
   the frozen sender-text and oracle-text controls. No prompt changes or stronger
   control tuning after final inspection. The analysis refuses a verdict without
   these records. Unique compact receiver messages are cached as registered.
6. `final_v2.py analyze` independently reconstructs scores from per-example
   records, validates tensor/JSON agreement, control construction, checkpoint
   and source hashes, and re-derives correct/shuffled/random/zero latent tensors
   from stored sender activations. It joins stronger text outputs by exact IDs,
   group and label, not by row-order assumptions. Bootstrap draws use the same
   nonce groups for every condition and contrast. Report per-class results,
   donor-following, mean/median margins, paired intervals and norm diagnostics.
7. Statistical PASS requires exactly the registered thresholds in
   PREREGISTRATION.md. Mechanics/provenance/control-construction failure instead
   makes the experiment uninterpretable; never turn an implementation failure
   into an intrinsic receiver limitation. Text need not lose for a channel PASS.
   No gain from a trained-on or reusable DEV set is called final evidence.

Any process failure leaves its directory and error record intact. No silent
restart or overwrite. Changes after final outcomes need a disclosed separate
attempt and cannot retroactively change this decision rule. A final PASS here
licenses the next synthetic cross-family gate, not Arabic or generation.

The original V1 source remains sealed. The V2 extension remains unchanged
through full training; final helper modules do not alter endpoint inference.
No cloud resources are created by this workflow; current external spend USD0.

## Sequential queue

`confirm.py` may be launched behind the existing live `develop.py` process. It
verifies that process identity while waiting, requires its terminal success,
then runs steps1–6 in separate sequential subprocesses. It performs a conservative
DEV readiness check using the already registered point thresholds (correct>=90%,
each class>=85%, randomized controls<=35%, zero/baseline25%) after selected-
checkpoint reproduction and stronger DEV text evaluation, before final freeze.
This is not a new checkpoint selector: only the minimum-DEV-CE checkpoint is
considered. If readiness fails, final data remain untouched. The queue stops on
any command failure, retains all logs, and never automatically restarts an attempt.
It does not provision resources or start cross-family work. The queue's own code
is included in the eventual freeze.
